# career-prep (이직준비)

이직 준비에서 반복되는 두 가지를 맡는 AI 스킬입니다.

1. **공고 서치**: 조건에 맞는 공고를 찾고, 열려 있는지 확인하고, 중복 없이 트래커에 쌓습니다.
2. **이력 DB 관리**: 내 경험과 성과를 구조화된 DB로 유지합니다. 새 성과 추가, 수치 정정, 오래된 항목 점검까지 합니다.

두 기능을 잇는 것이 **적합도 대조**입니다. 공고 요건과 이력 DB를 비교해 공백을 찾고, 그 공백이 다시 DB 보강 질문이 됩니다.
이 스킬은 이력서나 자소서를 쓰지 않습니다.

"나만의 Skill 만들기" 과제용으로, 실제 업무 흐름을 **하네스 엔지니어링 6요소**로 구성했습니다.

## 왜 만들었나

- 공고를 찾을 때마다 같은 공고를 또 보고, 마감됐는지 매번 다시 열어봅니다.
- 내 성과 수치가 문서마다 달라서, 어떤 게 맞는 값인지 헷갈립니다.
- 새로 한 일이 생겨도 정리할 곳이 없어서 기억에서 사라집니다.
- 공고마다 내 경험이 어디에 해당하는지 매번 처음부터 맞춰봅니다.

이 스킬은 "공고 트래커 + 이력 DB + 변경 이력"을 한곳에 고정하고, **승인 후에만 DB가 바뀌게** 합니다.

## 사용법

| 이렇게 말하면 | 경로 | 하는 일 |
|---|---|---|
| "이번 주 공고 찾아줘" | S 서치 | 검색 → 원문 확인 → 중복 제거 → 1차 적합도 → 트래커 |
| 공고 URL이나 원문 붙여넣기 | A 분석 | JD 저장 → 요약 → DB 대조 → 공백 |
| "이번에 한 일 추가해줘", "수치 정정" | D 업데이트 | 진술 → 구조화 → 충돌 확인 → diff → 승인 → 반영 |
| "DB 점검해줘" | C 점검 | 누락, 미검증, 오래된 항목, 중복, 충돌 보고 |

말투가 경로를 정하므로 "어떤 걸 할까요?"라고 되묻지 않습니다.

## 설계: 하네스 6요소

| 요소 | 이 스킬에서의 구현 | 위치 |
|---|---|---|
| **Role** | Scout(탐색) / Archivist(DB 기록) / Analyst(대조) / Auditor(검증). 만드는 역할과 채점하는 역할 분리 | `SKILL.md` §1, `references/roles.md` |
| **Rubric** | 서치 S1~S5, DB D1~D7 PASS/FAIL. 기준은 Auditor가 관리 | `SKILL.md` §2, `references/rubric.md` |
| **Context** | 검색 조건, DB, 변경 이력, 트래커를 필요한 시점에 읽기. 단계 간 인계는 파일로 | `SKILL.md` §3, `references/context.md`, `references/handoff-templates.md` |
| **Tools** | 웹 검색·조회, 드라이브, `validate_db.py`, 예약 알림(선택) | `SKILL.md` §4, `scripts/` |
| **Workflow** | 경로별 단계 + FAIL이면 최대 3회 재검증 | `SKILL.md` §5 |
| **Guardrail** | 작성·제출·발송 금지, 승인 없는 DB 변경 금지, 폐기 보존, 민감 정보 비저장, 실제 DB 비공개 | `SKILL.md` §6, `references/guardrails.md` |

### 적용한 하네스 원칙

1. **역할 분리**: 정리한 쪽이 자기 결과를 채점하면 후해지므로 Auditor를 따로 둡니다. 합격 기준은 Auditor만 바꿀 수 있습니다.
2. **컨텍스트 관리**: DB는 기억이 아니라 라이브 파일을 읽습니다. 세션이 바뀌어도 `work/*.md`와 `changelog.md`로 이어갑니다.
3. **측정 가능한 기준**: "잘 정리됐다" 대신 PASS/FAIL과 근거, 그리고 `validate_db.py`의 실행 결과를 요구합니다.

## 흐름

```
[S 서치]  조건 → 검색 → 원문 확인 → 중복 제거 → 1차 적합도 → 검증(S) → 트래커
[A 분석]  JD 저장 → 요약 → DB 대조 → 공백 ──(증거 공백)──┐
[D 업데이트] 진술 → 구조화 → 충돌 확인 → diff → 승인 → 반영 → changelog → validate ←┘
[C 점검]  스키마 / 미검증 / 오래됨 / 중복 / 충돌 보고
```

분석에서 나온 **증거 공백**이 DB 업데이트 질문으로 이어지는 것이 핵심입니다. 공고를 볼수록 DB가 채워집니다.

```
career-prep/
├── SKILL.md                      # 스킬 본문 (6요소 순서)
├── README.md
├── .gitignore                    # career-db/ (실제 데이터) 제외
├── references/
│   ├── roles.md                  # 역할별 세부 지침
│   ├── rubric.md                 # S1~S5, D1~D7 상세와 판정 양식
│   ├── context.md                # 저장 원칙, 상태 규칙
│   ├── guardrails.md             # 금지 사항과 질문 예산
│   └── handoff-templates.md      # 인계 파일, 변경 이력, 반환 양식
├── templates/
│   ├── experience-db.md          # 이력 DB 항목 양식
│   ├── search-criteria.md        # 검색 조건 양식
│   └── postings.csv              # 공고 트래커 양식

│   └── validate_db.py            # DB 스키마·지표·민감어 검사

    ├── sample-db.md              # 가상 이력 DB
    └── sample-run.md             # 경로 S/A/D/C 실행 예시
```

## 설치

- **Claude Code**: 이 폴더를 `~/.claude/skills/career-prep/` (전체) 또는 프로젝트의 `.claude/skills/career-prep/` 에 복사
- **claude.ai / Cowork**: 폴더를 zip으로 압축해 Skills에 업로드

설치 후 `templates/`를 복사해 `career-db/`를 만들고 본인 정보를 채우세요. `career-db/`는 `.gitignore`에 들어 있어 실수로 올라가지 않습니다.

## DB 검증 스크립트

```bash
python3 -I scripts/validate_db.py examples/sample-db.md
```

필수 필드, 역할·상태 값, 날짜 형식, 지표 4요소(값/단위/기간/귀속), 확정 항목의 `미확인` 값, 민감어를 검사합니다. 오류가 있으면 종료 코드 1을 반환합니다.

## 개인정보 처리

- 이 저장소에는 **템플릿과 가상 예시만** 있습니다. 실제 이름, 회사, 성과 수치는 없습니다.
- 실제 이력 DB, 검색 조건, 트래커는 `career-db/`에 두고 공개 저장소에 올리지 않습니다.
- DB에는 퇴사·휴직 사유, 연봉과 협상 정보, 회사에 대한 불만, 동료 사정을 저장하지 않습니다.

## 한계

- 서류 통과 확률은 계산하지 않습니다. 공고와 DB만으로는 경쟁자와 내부 사정을 알 수 없습니다.
- 한 모델이 여러 역할을 맡으면 역할 분리는 "읽는 관점의 분리"입니다. 더 엄격하게 하려면 서브에이전트로 Scout, Archivist, Auditor를 따로 띄우세요.
- 공고 검색 품질은 웹 검색 결과와 접근 가능한 페이지에 달려 있습니다. 로그인이 필요한 플랫폼은 확인 불가로 표시합니다.
- DB는 사용자의 진술만큼만 정확합니다. 지표에는 단위, 기간, 귀속, 분모를 꼭 적어 두세요.
